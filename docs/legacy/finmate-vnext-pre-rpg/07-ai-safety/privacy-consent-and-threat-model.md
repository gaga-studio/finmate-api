# 개인정보·동의 및 위협 모델

## 1. 보호 목표와 범위

FinMate는 마이데이터로 개인 목표를 계산하고, 별도 공개 동의를 한 사용자의 검증된 루틴만 익명 카드로 제공한다. 개인정보 보호 목표는 다음과 같다.

- 목표 계산에 필요한 최소 데이터만 수집하고 목적별 동의를 분리한다.
- 다른 사용자에게는 정확 금액과 식별 단서를 공개하지 않는다.
- 동의 철회가 추천 노출과 파생 데이터에서 정해진 시간 안에 실제로 반영된다.
- 목표·레이드·AI가 금융 행동을 압박하거나 투자 위험을 높이지 않는다.
- 계산과 공개 여부를 사후 재현하되 감사 로그가 새로운 개인정보 저장소가 되지 않게 한다.

친구·팔로잉과 메이트 찾기는 Phase 2다. MVP의 메이트 탭은 비교 탐색만 제공하며 사용자 간 연락, 검색, 초대, 메시지, 공동 목표를 제공하지 않는다.

3~4주 MVP는 계약 호환 어댑터와 합성 금융데이터로 이 흐름과 통제를 검증하는 프로토타입이다. 실제 마이데이터 수집·전송과 실제 사용자 동의 데이터 처리는 post-MVP 검증 범위이며 MVP 인수 증거로 요구하지 않는다.

## 2. 데이터 분류와 흐름

| 등급 | 예시 | 허용 처리 | 금지 처리 |
| --- | --- | --- | --- |
| P0 공개 | 익명 닉네임, 모험가 외형, 승인된 생활맥락 태그, 루틴 요약, 유지기간, 비율·빈도 구간, 기준일 | 공개 동의·표본·위험 검토 통과 후 카드 노출 | 정확 금액·원문으로 역변환 |
| P1 내부 가명 | `sourceProfileKey`, 유사그룹 ID, 후보·목표 ID, 동의 버전, AI 요청 ID | 서비스 운영·감사에 최소 사용 | 클라이언트 응답·분석 이벤트로 전송 |
| P2 민감 금융 | 정확 소득·잔액·지출·저축, 거래 원문, 계좌·상품·종목, 기준선 스냅샷 | 암호화 저장, 결정론적 계산 서비스에서만 사용 | AI 입력, 카드 공개, 일반 운영 로그 |
| P3 직접 식별 | 이름, 연락처, 이메일, 인증 식별자 | 인증·법적 의무에 필요한 분리 저장 | 추천 인덱스·AI·제품 분석과 결합 |

```text
마이데이터 제공자
→ 수집·정규화 저장소(P2, 사용자별 접근)
→ 계산 서비스(기준선·후보·진행률)
→ 공개 적격성·가명처리 서비스
→ 위험·표본 검토
→ 공개 카드 인덱스(P0 + P1 연결키)
→ 다른 사용자 비교 탐색(P0만)

계산 서비스
→ 허용 필드 선택·구간화
→ AI 게이트웨이(P0/P1의 제한된 ID·코드만)
→ 검증된 설명
```

직접 식별정보, 금융 원문, 공개 카드 연결키는 논리적·권한상 분리한다. 운영 분석 이벤트에는 사용자 가명 키만 쓰고 카드 원본 사용자의 키는 넣지 않는다.

## 3. 동의 체계

동의 화면은 목적, 항목, 보유기간, 제3자 제공 여부, 거부 효과, 철회 방법을 동의 단위별로 보여준다. 필수와 선택을 미리 체크하지 않으며, 마케팅 동의를 서비스 이용 조건으로 묶지 않는다.

| 동의 ID | 필수 여부 | 목적 | 주요 항목 | 철회 시 효과 |
| --- | --- | --- | --- | --- |
| `MYDATA_SERVICE` | 목표 계산 사용 시 필수 | 금융 기준선·목표·진행률 계산 | 선택한 금융업권의 수입·지출·저축 관련 정보 | 신규 동기화 중지, 데이터 상태 변경, 법적 보존 외 삭제 절차 시작 |
| `ANONYMOUS_CARD_SHARE` | 선택 | 검증된 루틴을 익명 카드로 공개 | P0 공개 필드 | 즉시 추천 제외, 24시간 내 캐시·파생 추천 제거 |
| `PRODUCT_ANALYTICS` | 선택 | 퍼널·품질 분석 | 가명 사용자 키, 화면·행동 이벤트, 오류 코드 | 신규 선택 분석 수집 중지, 보유 정책에 따른 삭제 |
| `AI_EXPLANATION` | 선택 | 서버 허용 목표 후보의 순위·설명 제공 | 허용된 카드 문맥·후보 ID, 구간, 근거 코드 | 신규·대기 AI 호출 즉시 중지, 결정론적 순위·설명 제공, 7일 내 모든 비법정 AI 연결 레코드·콘텐츠 삭제 또는 비가역 분리 |

`ANONYMOUS_CARD_SHARE`는 마이데이터 서비스 동의와 별도다. 공개를 거부해도 내 목표 계산과 비교 탐색 이용에 불이익이 없다. 동의 기록은 `consentId`, 버전, 표시 문안 해시, 선택 항목, 부여·철회 시각, 채널, 사용자 가명 키로 저장한다. 새 공개 항목이나 목적이 추가되면 기존 동의를 확장 해석하지 않고 재동의를 받는다.

### 3.1 버전·멱등·철회 우선 명령 계약

모든 공개 동의 변경은 `PUT /api/v1/me/privacy`의 aggregate 명령으로 처리한다. boolean 설정은 아래처럼 철회와 opt-in/update 명령을 명시적으로 구분하며, OpenAPI request·header와 `409`·`412` 응답이 이 계약을 고정한다.

| 계약 요소 | 필수 의미 |
| --- | --- |
| body `consentAggregateId` | 한 번 부여된 동의 aggregate UUID. `WITHDRAWN` 뒤 같은 ID를 재활성화하지 않는다. |
| body `expectedVersion` | 클라이언트가 읽은 현재 integer `version`이며 1 이상이다. |
| body `anonymousCardOptIn` | `false`는 `WITHDRAW`, `true`는 `OPT_IN_OR_UPDATE` 명령이다. |
| body `exposedFields`, `consentVersion` | 철회는 `exposedFields = []`, opt-in/update는 허용 공개 필드만 보낸다. 두 명령 모두 현재 동의 문안 version을 보낸다. |
| header `If-Match` | 직전 응답의 strong `ETag`이며 그 version은 body `expectedVersion`과 같아야 한다. 최신 version과 하나라도 다르면 `412 PRECONDITION_FAILED`다. |
| header `Idempotency-Key` | 사용자·operationId·request hash와 24시간 결합한다. 같은 key와 같은 payload는 최초 status·body·header를 재생하고, 같은 key의 다른 payload는 `409 IDEMPOTENCY_KEY_REUSED`다. |

명령 적용 순서는 다음으로 고정한다.

1. 같은 `consentAggregateId`와 `expectedVersion`에 경합 명령이 있으면 `anonymousCardOptIn = false` 철회를 먼저 직렬화한다.
2. 철회는 `actualVersion == expectedVersion`/`If-Match`를 확인한 뒤 `WITHDRAWN`, `version + 1`과 `consent.withdrawn` outbox event를 한 트랜잭션으로 커밋한다.
3. 뒤에 처리되는 opt-in/update는 이미 증가한 version과 맞지 않으므로 `412 PRECONDITION_FAILED`다. 응답 metadata는 `consentAggregateId`, `expectedVersion`, `currentVersion`, `currentState = WITHDRAWN`, `mutationApplied = false`를 제공한다.
4. 철회 뒤 늦게 도착한 opt-in, 재전송된 오래된 opt-in, offline queue의 opt-in은 새 `Idempotency-Key`를 사용해도 모두 `412`이며 공개 인덱스나 새 aggregate를 만들 수 없다. 같은 key·payload 재시도만 최초 응답을 그대로 재생한다.
5. 같은 aggregate의 `WITHDRAWN`은 terminal이다. 재동의는 사용자가 최신 문안을 다시 확인한 새 명시적 행동으로만 시작하고 새 `consentAggregateId`를 발급하며, 서버는 실패한 이전 명령을 새 aggregate로 변환하지 않는다.

성공 응답은 `consentAggregateId`, `anonymousCardOptIn`, `exposedFields`, `consentVersion`, `version`, `updatedAt`, `shareConsentState`를 필수로 포함하고 같은 version의 `ETag`를 반환한다. 조회·추천 gate는 캐시보다 이 aggregate의 최신 `shareConsentState`를 먼저 확인한다.

마이데이터의 정기 전송은 실시간이 아니다. 금융위원회의 [마이데이터 2.0 안내](https://www.fsc.go.kr/po010101/84780)에 따라 기본 주 1회, 사용자가 1주 간격으로 최대 한 달까지 선택할 수 있음을 동의와 데이터 상태 화면에서 설명한다.

## 4. 익명 카드 필드 정책

### 공개 가능

- 서비스가 발급한 익명 닉네임과 모험가 외형
- 사전 승인된 넓은 생활맥락 태그: `사회초년생`, `소득 규칙적`, `월세 부담 구간`
- 유사 이유 2~3개와 대표 루틴 1개
- 정량 루틴 90일 이상, 행동 루틴 30일 이상의 유지기간
- 5%p 이상 폭의 비율 구간 또는 충분히 넓은 빈도 구간
- 일 단위 데이터 기준일
- `금액 비공개 · 실제 루틴 · 공개 동의` 상태 안내

### 공개 금지

- 이름, 연락처, 이메일, 사용자 ID, `sourceProfileKey`
- 정확 소득·연봉·잔액·지출·저축 금액과 거래 원문
- 금융회사·계좌·카드·상품·종목명, 투자금, 수익률
- 상세 직장·학교·주소·지역, 생년월일, 정확 나이
- 희귀 질병·가족관계·채무 사유 등 민감한 생활정보
- 유사그룹 ID, 동의 버전, 내부 품질 점수와 원본 레코드 링크

카드는 공개 동의, 데이터 품질, 최신성, 유지기간, 정확 코호트 최소 30명, 루틴 지표 P10~P90, 재식별 위험 검토를 모두 통과해야 한다. 정확 코호트가 30명 미만이면 개인 카드를 만들지 않고 주거 세부형태·가구형태 같은 비금융 생활맥락만 결정적 순서로 일반화한다. 소득 규칙성·여윳돈·부채부담 구간·목표 안전범위는 넓히지 않는다. 처음 찾은 안전한 일반화 코호트가 30명 이상일 때만 개인 필드 없는 `GROUP_ROUTINE`을 만들며, 모든 허용 코호트가 30명 미만이면 `INSUFFICIENT`와 빈 카드 목록을 반환한다.

## 5. 철회·삭제·보존

### 공개 철회

1. 최신 `consentAggregateId`, `expectedVersion`/`If-Match`, `Idempotency-Key`와 `anonymousCardOptIn = false`를 가진 철회 명령을 같은 version의 opt-in/update보다 먼저 커밋하고 동의 상태를 `WITHDRAWN`으로 바꾼 뒤 공개 인덱스 조회 전 필터에서 제외한다.
2. 새 카드 생성, 재색인, AI 입력 생성과 분석 조인에서 즉시 제외한다.
3. CDN·API·클라이언트 캐시와 파생 추천 큐에 삭제 이벤트를 보내고 24시간 이내 제거한다.
4. 삭제 작업은 멱등적으로 재시도하고 완료 시각과 제거 대상 수를 감사 기록에 남긴다.
5. 다른 사용자가 이미 확정한 목표에서는 원본 사용자 연결을 제거하고 템플릿, 루틴 출처 유형, 확정 당시 계산 버전만 남긴다.

공개 철회 SLA는 조회 경로 즉시 차단 5분 이내, 캐시·파생 추천 완전 제거 24시간 이내다. P95와 최대 시간을 매일 측정하며 24시간 초과 1건은 개인정보 사고 절차로 분류한다.

### AI 기록 보존

아래 정책은 개인정보 문서와 AI 코치 문서가 함께 사용하는 단일 보존 계약이다.

| 레코드 분류 | 일반 보존 | `AI_EXPLANATION` 철회 또는 계정 삭제 |
| --- | --- | --- |
| `OPERATIONAL` | AI 동의가 유효한 일반 운영 로그도 `createdAt`부터 최대 90일이며 더 짧게 설정할 수 있다. 원문 모델 입력·출력은 기본 저장하지 않는다. | 연결된 모든 레코드·콘텐츠·ID·해시·가명 매핑·재연결 키를 7일 이내 삭제하거나 다시 연결할 수 없게 비가역 분리한다. |
| `INCIDENT_EVIDENCE` | 유효한 사고 티켓에 필요한 최소 필드만 별도 저장하며 `retentionExpiresAt`은 생성 시 필수, 최대 180일이다. 티켓이 닫히거나 증거 필요성이 끝나면 더 일찍 삭제하고 자동 연장하지 않는다. | 이 분류는 철회·삭제를 넘겨 존속할 수 없다. 해당 사건 전에 `LEGAL_REQUIRED`의 모든 필드와 법무 승인을 갖춰 완전히 재분류되지 않았다면 7일 이내 삭제한다. 단순 비식별화나 열린 사고 티켓은 예외가 아니다. |
| `LEGAL_REQUIRED` | `legalBasisCitation`, `retentionExpiresAt`, `recordScope`, `approvedBy`, `legalCaseId`, `legalApprovedAt`이 모두 있고 구체적 법적 근거가 확인된 최소 레코드만 각 만료일까지 격리 보관한다. | `legalApprovedAt`이 철회·삭제 요청 시각보다 앞선 완전한 재분류만 예외다. 사건 뒤 사후 분류하거나 누락 필드를 보충해 보존을 연장할 수 없다. |

백업은 레코드 분류와 무관하게 최대 30일 안에 만료한다. 철회·삭제 tombstone은 모든 백업 복원에 서비스 개방 전에 재생하며, tombstone 대상이나 재연결 가능한 가명 매핑이 한 건이라도 복원되면 복원을 실패 처리한다.

### 서비스 데이터 삭제

- 본인 확인 후 삭제 범위와 목표·기록에 미치는 영향을 보여주고 요청을 접수한다.
- 활성 세션과 전송 토큰을 폐기하고 신규 수집·AI·분석 처리를 중지한다.
- 운영 DB, 검색 인덱스, 공개 카드, 분석 사용자 프로필과 비법정 파생 데이터를 7일 이내 삭제한다. AI 영역은 `OPERATIONAL`, `INCIDENT_EVIDENCE`를 포함한 모든 non-`LEGAL_REQUIRED` 연결 레코드와 콘텐츠를 삭제하거나 비가역 분리한다.
- 인증 사용자 ID와 서비스·분석·AI 가명 사이의 매핑 및 재연결 키를 7일 이내 삭제·폐기한다. 남은 비식별 집계나 해시는 계정 또는 서로 다른 저장소를 다시 연결할 수 없어야 한다.
- 백업은 격리 상태로 두고 최대 30일 이내 만료시키며 복원 시 철회·삭제 tombstone을 재적용한다.
- 법적 보존이 필요한 동의·접근·사고 감사 기록은 운영 레코드와 분리하고 최소 필드만 저장한다. 각 레코드에 `recordClass=LEGAL_REQUIRED`, `legalBasisCitation`, `retentionExpiresAt`, `recordScope`, `approvedBy`, `legalCaseId`, `legalApprovedAt`을 기록하며 하나라도 없거나 `legalApprovedAt`이 철회·삭제 요청 뒤라면 법정 보존 예외로 분류할 수 없다.
- 법적 저장소는 서비스 가명 대신 사건 전용 가명을 사용한다. 재연결 매핑은 법무 승인 역할만 조회할 수 있고 만료 시 기록·매핑·백업 삭제표시를 함께 제거한다.
- 완료 통지에는 삭제 완료 범위, 법적 보존 항목의 범주와 만료 기준을 제공한다.

정확한 법정 보존기간은 출시 전 개인정보·법무 검토에서 근거별로 확정한다. 근거가 확정되지 않은 데이터는 서비스 기본 최소기간을 넘겨 보관하지 않는다.

### 삭제 원장과 복원

- 삭제 tombstone 원장은 `deletionId`, 대상 범주, 요청·완료 시각, 결과, 법정 보존 분류 ID만 보관하고 인증 ID·금융값·삭제된 가명을 복제하지 않는다.
- 삭제 작업은 멱등적이며 계정 삭제, `AI_EXPLANATION` 철회, `PRODUCT_ANALYTICS` 철회와 공개 철회를 범주별로 추적한다.
- 백업 복원 시 서비스 트래픽을 열기 전에 철회·삭제 tombstone 원장을 재생하고, 삭제 대상 0건 재등장과 가명 매핑 0건을 자동 검증한다. 한 건이라도 발견되면 복원을 실패 처리한다.
- 운영·법적 저장소 백업은 모두 최대 30일 안에 물리 만료한다. 법적 원본 레코드는 각 `retentionExpiresAt`까지 격리할 수 있지만 30일을 넘는 별도 backup 사본을 만들 수 없고, 만료된 사건 기록은 복원할 수 없다.

## 7. 게임화 안전 통제

- 투자 거래, 투자금, 수익률, 상품 가입을 목표·퀘스트·성장·축하의 근거로 사용하지 않는다.
- 공개 순위, 사용자 간 기여도 경쟁, 손실·강등·보스 회복, 재도전 횟수를 만들지 않는다.
- 목표 미달, 일시정지, 데이터 지연에는 불이익을 주지 않는다.
- 푸시는 사용자가 정한 일정, 데이터 반영, 개인정보 안내로 제한한다. 시세 급등락, 실시간 종목, 반복 행동을 자극하는 알림을 금지한다.
- 레이드 연출 강도를 줄이거나 끌 수 있고, 설정과 무관하게 동일한 금융 기능을 이용할 수 있어야 한다.
- 비교 화면은 상대의 정확 금액이 아니라 검증된 루틴을 내 데이터에 맞게 가공한다는 점을 명시하고 압박·수치심 표현을 금지한다.

FCA의 [거래 앱 디지털 참여 기법 실험](https://www.fca.org.uk/publications/fca-research/research-note-digital-engagement-practices-trading-apps-experiment)은 깜박이는 가격, 푸시 알림, 리더보드, 보상 추첨 같은 기법이 거래 빈도와 투자 위험을 높일 수 있음을 보고했다. FinMate는 이를 근거로 투자 학습·점검과 거래 행동을 분리한다.

## 8. 운영 검증과 사고 대응

출시 전 개인정보 책임자, 보안 담당자, 제품 책임자가 다음을 승인한다.

- 데이터 흐름과 처리 목적, 동의 문안·버전, 공개·비공개 필드
- 재식별 위험 평가와 표본·구간·억제 규칙
- 위탁·제3자 제공 관계, 국외 이전 여부, AI 제공자 데이터 보존 설정
- 보존·삭제 기준과 백업 삭제 재적용 절차
- 침해·오노출·동의 위반 탐지, 통지와 신고 의사결정 절차

사고 발생 시 `탐지 → 공개·AI·분석 경로 차단 → 증거 보존 → 영향 범위 확인 → 책임자·법무 판단 → 사용자 보호·통지 → 재발 방지 테스트` 순서로 처리한다. 비허용 개인정보 노출, 철회 후 24시간 초과 노출, 투자 유도 보상은 심각도 1로 취급하고 출시·배포를 중지한다.

개인정보보호위원회의 [2026 가명정보 처리 가이드라인](https://www.pipc.go.kr/np/cop/bbs/selectBoardArticle.do?bbsId=BS074&mCode=C020010000&nttId=11928)에 따라 `사전 준비 → 위험성 검토 → 가명처리 → 적정성 검토 → 안전한 관리` 절차를 문서화한다. 내부 활용과 외부 제공의 처리 환경 차이를 위험 평가에 반영하고, 공개 카드처럼 외부에서 볼 수 있는 결과는 더 엄격한 재식별 검토를 적용한다.
