# FinMate vNext 내부 킥오프 덱 구성

> 상태: Review  
> 대상: 기획·디자인·프론트엔드·백엔드·데이터 작업에 참여하는 전체 팀  
> 목적: 발표 설득이 아니라 구현 기준과 첫 주 결과를 합의한다.

| 장 | 결론형 제목 | 핵심 내용 | 회의에서 확정할 것 |
| ---: | --- | --- | --- |
| 1 | `이번 재개발은 하나의 행동 루프만 완성합니다` | 한 줄 정의, 핵심 루프, 3~4주 범위 | 루프와 기간 |
| 2 | `MVP는 비교 탐색 하나를 깊게 만들고 나머지는 경계만 남깁니다` | 실제 동작 범위와 Phase 2 | MVP 경계 |
| 3 | `추천 모험가는 목표값이 아니라 검증된 루틴의 출처입니다` | 카드 표시 정보, 발견·가공·확정 | 카드 공개 범위 |
| 4 | `하나의 대표 흐름이 모든 화면·API·테스트의 기준입니다` | 기준선부터 기록까지 8단계 | 대표 흐름 |
| 5 | `목표의 값과 기간은 AI가 아니라 템플릿·코드·사용자가 결정합니다` | 목표 생성 책임과 예시 | 목표 확정 UX |
| 6 | `코드가 금융을 계산하고 게임은 상태를 번역합니다` | 네 동물과 네 책임의 분리 | 계산 책임 |
| 7 | `MVP 화면은 정상 상태보다 예외 상태를 먼저 함께 정의합니다` | 8개 화면과 6개 공통 상태 | 화면 범위 |
| 8 | `프론트와 백엔드는 합성 MyData 어댑터와 OpenAPI를 사이에 두고 분리합니다` | PWA·API·DB·어댑터·AI 경계 | 기술 구조 |
| 9 | `OpenAPI 예시가 프론트 fixture와 백엔드 인수 기준을 동시에 만듭니다` | 핵심 모델과 계약 흐름 | API 우선 개발 |
| 10 | `개인정보와 게임화 가드레일은 부가 정책이 아니라 기능 요구사항입니다` | 동의·철회·AI·투자 보호 | 출시 차단 기준 |
| 11 | `완료는 화면이 보이는 것이 아니라 계약과 핵심 E2E가 통과하는 것입니다` | QA 층과 완료 정의 | Definition of Done |
| 12 | `3~4주는 계약 → 핵심 루프 → 검증 순서로 씁니다` | 주차별 WBS와 범위 축소 원칙 | 일정 승인 |
| 13 | `개발 시작 전에 같은 제품을 보고 있습니까?` | 착수 체크와 미결정 항목 처리 | 착수 승인 |

## 발표 원칙

- 장마다 결론 하나만 사용한다.
- 기능 목록보다 입력·처리·출력·예외를 보여준다.
- Phase 2 기능은 별도 색으로 표시하고 개발 작업으로 분해하지 않는다.
- PPT에서 생긴 새 결정은 반드시 원본 문서로 되돌려 반영한다.
